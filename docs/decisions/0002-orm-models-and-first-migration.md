# 0002. ORM models and the first migration

Status: accepted
Date: 2026-07-28

## Context

`docs/schema.md` is the data contract but left several choices as open questions marked
`TODO`. To build the SQLAlchemy models and the first Alembic migration, some of those had to be
answered now. This record explains the choices so the team can revisit them at the first
meeting rather than reverse-engineer them from the code. All of these are reversible with a
follow-up migration.

## Decisions

### Enums are stored as plain text for now, with reference value sets in code

The schema left "Postgres enum vs lookup table vs plain string" open per enum, and several
value sets are not finalized. Every enum-like column (`player.status`, `user.role`,
`organization.type`, and so on) is a plain `TEXT` column. The intended values live as
`StrEnum` classes in `apps/api/app/models/enums.py`, used by the application and pipeline
validation layers.

Why: a native Postgres enum or a `CHECK` constraint would turn every future value change into
a migration, and the sets are still moving. Text plus an application-level enum keeps the
database flexible now and lets us promote hot, settled enums to a database constraint later.

### User email uniqueness is a functional unique index on `lower(email)`

The schema specified `citext` for `user.email`. `citext` needs its own extension and there is
no first-party SQLAlchemy `citext` type (it would add a dependency). Instead the column is
`TEXT` with a unique index on `lower(email)`, which gives the same case-insensitive uniqueness
guarantee with no new dependency. Revisit if we adopt `citext` project wide.

### UUID primary keys default to `gen_random_uuid()`

Primary keys are UUIDs generated by the database via `gen_random_uuid()`, which is built into
PostgreSQL 13+ (the stack runs Postgres 16), so no `pgcrypto` or `uuid-ossp` extension is
required.

### The first migration is hand written, not autogenerated

`0001_create_core_tables` was written by hand rather than produced by
`alembic revision --autogenerate`, because a database was not available in the session where
the models were implemented. It was validated two ways without a live database: the models
were rendered to PostgreSQL DDL, and the migration was rendered to SQL with
`alembic upgrade head --sql`. The output matches the models. The next person to run against a
real database should confirm `alembic upgrade head` applies cleanly and that a fresh
`--autogenerate` produces an empty diff.

## Deferred (left as TODO in the models, not built yet)

- `player_organization` "no overlapping active affiliations of the same role" constraint. It
  needs an exclusion constraint (`btree_gist`); left as a follow-up.
- `audit_log` append-only enforcement (no `UPDATE` / `DELETE`) via a trigger or role
  permissions. The model documents the rule; the database does not yet enforce it.
- Guardian-name-required-for-minors enforcement on `consent` (application layer).
- `pgvector` embedding storage for player similarity, pending the ML workstream's model choice.

## Consequences

- The data-engineering track can now build the synthetic data generator against real tables.
- The security and application tracks have `user`, `consent`, and `audit_log` to build auth,
  RBAC, and the integrity board on.
- The deferred items above are real gaps a reviewer should know about, not oversights.
