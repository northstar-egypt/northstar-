Integrity board

A work queue, not a dashboard. Every fraud, duplicate, and anomaly flag the models raise arrives here and a human decides. This is also the screen that produces the labelled outcomes the detectors are graded against, so its design has consequences for the ML track.

Annotations

  1. Three flag types, one queue. Fraud, duplicate, and anomaly are different models with different evidence, but they are the same job for the person doing the reviewing: look, decide, move on. Splitting them into three screens would triple the navigation and halve the throughput.
  2. Confidence is shown as the model's number, not converted into words. A reviewer who sees 0.91 on a case they then dismiss learns something about the detector. A reviewer who only ever sees "high" learns nothing, and the ML track loses the feedback.
  3. Evidence before verdict. The reasons the flag was raised are the first thing in the panel, above the buttons. A reviewer must be able to disagree with the model, which means they need to see what it actually matched on rather than a score alone.
  4. The diff is the actual work. For a duplicate this is the whole decision, and it needs to show which record has more history, because that determines which one survives the merge. The schema supports this directly through merged_into.
  5. Three outcomes, not two. "Needs more information" is a real state: the reviewer has to ring the academy. Without it, cases that cannot be decided today get dismissed to clear the queue, which quietly poisons the labelled data the detectors are scored against.
  6. A reason is captured with every decision. This is the screen's second job. Each decision plus its reason is a labelled example, and labelled examples are what precision and recall are computed from. A dismissal with no reason is a lost training signal.
  7. History is visible on the case, so two reviewers do not both work the same flag, and so a decision can be revisited later with its context intact.

Data and API

  • There is no flag table in the schema. docs/schema.md defines eight tables and none of them hold a raised flag with a status and a reviewer decision. This screen cannot be built until that exists, and it is the largest single gap the wireframing exercise found.
  • Merging writes merged_into on the losing Player and sets its status to merged. The schema already supports this, which is a good sign that the dedup thinking was done early.
  • Every decision appends to AuditLog with the reviewer, the outcome, and the reason.
  • The reviewer needs to reach the underlying player profiles from here, and those views are themselves audited.

Open questions

The missing table

A flag needs at minimum: what raised it, which model and version, the target player, a type, a confidence, the evidence, a status, the reviewer, the decision, the reason, and timestamps. That is a real table and it belongs in the shared core, because the ML track writes it, the application track reads it, and the security track audits it. Proposing it is a change to the data contract, which the repository's conventions say goes through a pull request that flags the affected workstreams. This wireframe is the argument for it.

  • Is a merge reversible? It should be, and that is easier to design now than to retrofit.
  • Does the flagged player or their coach get told? Being flagged for fraud without ever knowing is hard to defend, and telling people immediately makes the flag easier to game. This needs a policy, not a default.
  • Who reviews a flag against a player at the reviewer's own organization? An academy officer clearing flags on their own academy's records is a conflict of interest the role model does not currently prevent.
  • Do dismissed flags come back if new data arrives? If the detector reruns nightly it will raise the same case forever unless dismissal is remembered.
