Annotations

  1. No role picker. The role lives on the user record, so asking the user to choose one would be both redundant and a way to probe what roles exist. After a successful sign in the app routes by role: coach to the dashboard, scout to search, federation to oversight, player to their own profile.
  2. One error slot, one message. A wrong email and a wrong password produce the same text, so the form cannot be used to discover which accounts exist. The message is reserved in the layout rather than injected, so the form does not jump when it appears.
  3. Self submission is a separate door. Table tennis players seeking clubs abroad are a real user group who arrive with no account and no invitation. They need a way in that is not "ask your coach". Where that flow leads is not drawn yet, and it is deliberately not the same as creating a full account.

Data and API

  • Reads nothing before authentication. Posts email and password to an auth endpoint that does not exist yet.
  • On success it needs back at minimum: the user id, the role, and the organization id, because every screen after this one scopes on those three.
  • Writes login.success or login.failure to AuditLog. That is a security track concern but it is worth saying here that the frontend does not do it, the API does.

Open questions

For the security workstream

Session handling shapes this screen more than anything visible on it. If tokens are held in memory, "stay signed in" needs a refresh token and the checkbox is real. If sessions are cookie based, the checkbox controls cookie lifetime instead. If neither is decided, the checkbox should come off the wireframe rather than imply a capability we have not built. The auth decision record is listed as the security track's next task, so this screen waits on it.

  • Is there a registration flow at all, or are accounts created by an administrator and handed out? The schema has no invitation table, which suggests the second.
  • Rate limiting on failed attempts is assumed but not designed. It changes this screen only if we show the user something after repeated failures.
